Fleet · how it is actually wired

One encoder per stream, one relay for the whole audience

The two tiers scale on different things, which is the reason they are managed differently. An encoder is per stream: ten stations means ten tasks. A relay is per audience: ten stations is ten connections into it, and the load is the listeners on the other side. Everything below follows from that, including the honest answer to whether relays autoscale, which is no.

Does it manage relays the way it manages encoders?

Short answer: it balances across them, it does not create them. Neither tier autoscales.

 Encoder tierRelay tier
Unit one task per running stream one long-lived box carrying many stations
Created by the orchestrator, automatically, on every start a person, via POST /api/platform/relays
Destroyed by the orchestrator on stop, plus the reaper for dead ones nobody. A relay is retired by moving it to draining, then offline, by hand
Placement ECS capacity providers, spot weighted 4 to on-demand 1 with a base of 1 n/a — the relay is the machine
Assignment per run, ephemeral, no affinity sticky, stored on channels.relay_id, survives restarts
Balanced on left to ECS placement fewest assigned stations, ties broken on name so two control-plane replicas choose alike
Capacity limit none enforced by VOLT max_listeners is stored and editable and nothing reads it — pickRelay ignores it
Autoscaling no. ECS places tasks on capacity that already exists; VOLT never decides to add a machine no. Adding a relay is a deliberate act
Cost driver task-seconds → usage_accruals egress → relay_accruals, compared against cost_actuals
So, to your question

Yes to multiple relays, and it spreads stations across them automatically and stickily. No to creating them: a relay exists because somebody registered one. That is a defensible place to stop, because a relay is a long-lived box with a DNS name that listeners are pointed at, and conjuring one mid-broadcast is not the same kind of act as starting an encoder task that nobody outside the platform can see.

The one loose thread

max_listeners exists on the table, is settable through the admin API, and is read by nothing. A capacity number that is recorded and never enforced will eventually be believed by somebody. Either pickRelay should skip a relay that is at its limit, or the column should go.

What you can see today

Three states: built and rendered, API only, or absent.

Built

Which streams are on a host

Fleet & Usage answers this properly. Per host: instance type, availability zone, region, spot or on-demand, vCPUs and memory, the newest CPU / memory / network reading, your task count against the total on the machine so a shared box is visible, and a list of the streams with each one's task kind.

Absent readings render as unknown rather than zero, because a host drawn at 0% CPU when nothing has reported for an hour invites a conclusion.

Missing

Which host a stream is on

The reverse lookup. Live Streams shows no host at all — you get the five gates, uptime, viewers and group, and to find the machine you have to go to Fleet & Usage and scan. The data is one join away: instances.host_id already points at compute_hosts.

API only

Relay health

GET /api/platform/relays returns, per relay: stations assigned, how many of those are live, uptime, and the newest CPU / memory / network sample, plus a stale flag for a relay we can see but cannot currently measure.

Nothing renders it. System Admin has no relay panel.

API only

What is on a relay

GET /api/platform/relays/:id/stations lists every station pointed at a relay with its status and the account it belongs to. This is the direct answer to "what is on this box". Also unrendered.

Why the relay views are platform-only, deliberately

They sit behind requirePlatform and have no route on the tenant API at all, rather than a tenant route that checks a role. Two reasons, both commercial. Relay topology is shared infrastructure, so one tenant learning which relay carries their stations learns which relay carries everyone else's. And relay_accruals against cost_actuals is the platform's own cost basis: showing a customer what their traffic costs us to serve tells them our margin, and they will ask for it back. An account admin still gets everything about their own account, because usage_accruals is account-scoped and stays where it is.

On your Mac, right now

run-on-mac.sh starts one container called volt-icecast on :8000, and your database has no relays rows. So you are on the environment fallback path in the second diagram: every station points at localhost:8000, nothing is assigned, and none of the fleet logic runs. That is the intended behaviour for a development machine, and it is worth knowing that what you are testing is the single-relay mode, not the tier.

To exercise the real path locally you would register a relay row through the admin API pointing at that same container, at which point relay_id starts being written and the health endpoint has something to report.

What I would add, smallest first

  • The host on the Live Streams card. One join and one chip, and it closes the reverse lookup that is missing today. It is the thing you actually asked for.
  • A Relays panel in System Admin. The API is already there and already returns the right shape, including the stale flag. This is rendering, not plumbing.
  • Enforce max_listeners in pickRelay, or drop the column. Recorded and unenforced is the worst of the three options.
  • Relay assignment on the station page. A station's detail page never says which relay it is pushing to, which is the same reverse-lookup gap one tier down.
